### 统一同步模式
所有服务现在采用统一的双写双向同步模式：
- **写入**：`localStorage.setItem()` + `import('./cloudbase').then(...)` 异步双写到 CloudBase
- **读取**：先从 localStorage 同步读取，首次调用时异步从 CloudBase 合并增量数据回写 localStorage
- 使用 `_xxxCloudSyncInitiated` 标志确保只触发一次云同步

## 自检 Bug 修复（第二轮）

### Bug 1（严重）：异步回调用旧引用覆写 localStorage
**文件**：gameProposalService, marketplaceService, platformGameStoreService, voucherItemService

异步 CloudBase 合并回调使用了同步阶段捕获的 `data` 数组引用。如果在异步回调完成前有其他代码向 localStorage 写入了新数据（如 `saveProposals()`），回调会用旧数据覆写新数据。

**修复**：异步回调内重新读取 localStorage 最新数据（`localStorage.getItem()`），类似 `redeemCodeService.ts` 的 `initCloudSyncIfNeeded()` 已正确实现。

### Bug 2（严重）：VoteVoucherService 整体替换缓存
`cloudSync.then(merged => { voteCyclesCache = merged })` 用基于旧 localStorage 数据的 merged 数组整体替换缓存，丢失期间新创建的投票周期。

**修复**：改为增量合并（逐项 push），仅添加缓存中不存在的项。

### Bug 3（严重）：publishedGameService null 缓存崩溃
异步回调访问 `_publishedGamesCache!.map()` 时，缓存可能已被 `invalidateGamesCache()` 置为 null，导致 TypeError 被 `.catch(() => {})` 静默吞掉。

**修复**：异步回调内重新从 localStorage 读取数据，不依赖缓存引用。

### Bug 4（中等）：僵尸数据 — 已删除条目从云端复活
所有使用 `loadWithCloudSync` 的服务（VoteVoucherService, UserPoolService, PlatformBindingService, AlgorithmVoucherService, publishedGameService）存在僵尸数据 bug：已删除的条目通过 CloudBase 合并"复活"。

原因：`merged = [...originalLocalData, ...cloudOnlyItems]`，异步回调遍历 `merged` 添加不在当前 Map 中的项，但已删除的项（在 originalLocalData 中但已从 Map 删除）会被重新添加。

**修复**：在加载时捕获 `originalIds`（初始本地数据 ID 集合），异步合并时跳过 `originalIds` 中的项（这些要么已在 Map 中，要么已被删除，都不应从云端重新添加）。

### Bug 5（严重）：platformConfigService 集合名不匹配
`saveConfig()` 写入 `platform_treasury` 集合（结构 `{ id: 'platform_config', config: {...} }`），但 `syncFromCloud()` 从 `platform_config` 集合读取（不同集合名 + 不同数据结构）。云同步永远读不到数据。

**修复**：`syncFromCloud()` 改为从 `platform_treasury` 集合读取，并正确提取 `config` 字段。

## 上线前数据可靠性修复（第三轮）

### 背景
用户确认匿名登录已开启。控制台仍有 CloudBase 报错（初始化时序竞态、Skills 降级、marketplace 只同步 20 条等）。平台准备上线，必须保证数据不丢失。

### 根因分析
1. **初始化时序竞态**：`main.tsx` 中 `initCloudBase()` 和 `initializeSkills()` 并行调用，Skills 的 `onInitialize()` 在 CloudBase 就绪前执行，导致 AuthSkill/WalletSkill/GameConnectorSkill 永久降级为 localStorage/内存模式
2. **写入静默失败**：`dualWrite.ts` 的 `cloudWrite()` 用 `isCloudBaseReady()` 检查，未就绪时直接返回 `{ success: false }`，调用方 `save()` 不 await cloudWrite
3. **marketplace 数据丢失**：`saveListings()` 用 `listings.slice(-20)` 只同步最后 20 条
4. **AuthSkill 永久降级**：在 `onInitialize` 中缓存 `cloudbaseAuth`，初始化时 CloudBase 未就绪则永久为 null

### 修改文件

1. **src/main.tsx** — 修复初始化顺序：`initCloudBase().then(() => initializeSkills())`，确保 Skills 在 CloudBase 就绪后初始化
2. **src/services/cloudbase.ts** — 新增 `waitForCloudBase()`：返回 initPromise 或启动初始化，用于写入路径等待就绪
3. **src/services/dualWrite.ts** — `cloudWrite/cloudUpdateWhere/cloudDelete` 改用 `await waitForCloudBase()`；`save()/saveAll()/remove()` 中的 cloudWrite 改为 await
4. **src/services/marketplaceService.ts** — 移除 `slice(-20)` 限制；使用 `waitForCloudBase` + `Promise.allSettled` 并行同步所有活跃+近期变更的挂牌
5. **src/skills/auth/AuthSkill.ts** — 移除 `cloudbaseAuth` 缓存，改为 `getAuth()` 延迟获取；移除多余的 `aCoins` 字段
6. **src/skills/game-connector/GameConnectorSkill.ts** — CloudBase 数据加载改为 `ensureLoadedFromCloud()` 延迟+可重试模式

## 写入队列（writeQueue）Bug 自检修复（第四轮）

### 背景
统一写入重试队列实施完成后，全面自检15个改动文件的逻辑正确性。

### Bug 修复清单

1. **RETRY_DELAYS 笔误（中）** — `writeQueue.ts` 第58行 `[1000,2000,4000,80000,16000]` → `8000`。第4次重试应为8秒而非80秒。
2. **dualWrite save/saveAll 产生重复文档（高）** — `createDualStore.save()/saveAll()` 调用 `cloudWrite(collection, item)` 无 docId → 触发 `operation:'add'`，每次保存已有记录都会在 CloudBase 创建重复文档。改为 `cloudUpsert`。
3. **WalletSkill 交易记录重复（中）** — 交易入队用 `operation:'add'`，网络超时后重试会产生重复交易。改为 `upsert`（tx 有 id 字段）。
4. **WalletSkill 初始用户文档重复（中）** — 首次创建用户文档用 `add`，重试产生重复。改为 `upsert` + `where:{_openid:userId}`。
5. **platformTreasuryService 交易重复（中）** — 同上，交易入队用 `add` → 改为 `upsert`。
6. **writeQueue 队列满淘汰策略不合理（低）** — `getOldestEntry()` 按 createdAt 淘汰，不区分 failed/pending。修复为优先淘汰 failed 项，避免丢弃待处理写入。

### 未修复（已知限制，非Bug）
- `persistQueue()` 过滤 processing 项：页面刷新时正在处理的条目会丢失队列追踪，但数据已在 localStorage 中，不会真正丢失。
- `persistWithCloudSync` 每次全量入队：性能问题非数据问题，upsert 幂等保证不会产生重复。
