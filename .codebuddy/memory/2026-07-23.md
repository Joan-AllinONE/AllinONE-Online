## 第三次修复：活动中心空白 + 控制台无报错的真正根因（异步初始化竞态）

用户反馈"依然为空，但控制台无报错"。后端已确认 200+9 条数据，前端数据链路代码也正确。最终定位为 `main.tsx` 的**异步初始化竞态**：

- `main.tsx` 第24-55行：`initCloudBase().then(initializeSkills).then(() => installActivityModule(...))` 是**异步链**，activity skill 注册要等 CloudBase 初始化后才执行。
- `main.tsx` 第69行：`createRoot(...).render(<App/>)` 是**同步立即执行**的 → `ActivityCenter` 挂载时 skill 还没注册。
- `ActivityCenter` 的 `useEffect` 立刻 `refresh()` → `skillGateway.execute('activity','getActivities')` → skill 未找到 → 返回 `skillNotFound`（`{success:false}`）→ `useActivity` 把 `activities` 置为 `[]` → 空白，**且无报错**（skillNotFound 是正常响应不抛异常），且 `refresh` 不再重跑 → 永久空白。

**修复**：在 `src/activity/index.ts` 新增模块级"就绪信号" `getActivityModuleReady()`（installActivityModule 注册 skill 后 resolve）；`src/activity/hooks/useActivity.ts` 的 `refresh` 在拉取前 `await getActivityModuleReady()`（带 8s 安全超时兜底，防极端情况下永久卡加载）。

**验证**：`tsc -p tsconfig.json` 活动模块 0 错误；vite HMR 接受修改（page reload 无报错）。本机 agent-browser 因网络受限未能安装，故未做浏览器实跑验证（逻辑已确认无误）。

**经验**：凡"明明数据对了却空白且无控制台报错"的场景，优先怀疑 (1) 依赖单例/服务未就绪的初始化竞态，(2) execute 返回 success:false 被静默置空。

## 第四次修复：Vite HMR 导致 getActivityModuleReady Promise 永不 resolve（根本修复）

上一轮用 `getActivityModuleReady()` Promise + 8s 超时兜底，但用户反馈"依然为空、控制台无报错"，且控制台无任何 `activity.getActivities` 的 SkillGateway 调用日志。

**根因**：Vite HMR 修改 `index.ts` 后创建新模块实例，新实例的 `_activityModuleReady` Promise 是**未 resolve 的新 Promise**。旧的 `installActivityModule` 调用 resolve 了旧模块实例的 `_resolveActivityModuleReady`，对新模块无效。`useActivity.refresh()` 的 `await getActivityModuleReady()` 挂在新 Promise 上→永不 resolve→即使 8s 超时也不触发（HMR 状态与原 setTimeout 上下文不一致）。`refresh()` 永远不执行 `skillGateway.execute('activity',...)` → 控制台无调用日志、activities 空数组、空白且无报错。

**根本修复**：放弃 Promise 信号机制，改用**同步注册**：
1. `main.tsx`：把 `installActivityModule` 从 `initCloudBase` 异步链末尾移到 `createRoot().render()` **之前同步执行**。`installActivityModule` 仅依赖 `skillGateway`（同步单例）+ `getUserId`/`getUserName`（读 localStorage），无需等 CloudBase。skill 在任何组件挂载前就注册完毕，彻底消除竞态。
2. `useActivity.ts`：移除 `import { getActivityModuleReady } from '../index'` 和 `await getActivityModuleReady()` ——不再需要等待信号。
3. `index.ts`：移除 `_activityModuleReady`/`_resolveActivityModuleReady`/`getActivityModuleReady()` ——不再需要 Promise 机制。

**核心教训**：Vite HMR 会创建新模块实例，模块级 Promise/闭包状态在 HMR 后会"脱节"（旧 resolve 对新实例无效）。用 Promise 做"就绪信号"在 HMR 环境下不可靠；**同步注册才是 HMR-safe 的方案**。

## 第五次修复：真正的根因——两个 SkillGateway 单例实例（活动中心永久空白）

同步注册后依然空白、无报错、控制台无 `activity.getActivities` 调用日志。排查发现**两个 skillGateway 单例实例**：

- **实例 A**（`skills/index.ts` 第37行）：`new SkillGateway({ debug: true })` → main.tsx 和所有 skill 注册都在此实例上
- **实例 B**（`SkillGateway.ts` 第414行）：`getDefaultGateway()` → useActivity.ts 和 PublishedGameRuntime.ts 从此导入

useActivity 调用 `skillGateway.execute('activity','getActivities')` 用的是实例 B → 实例 B 无 activity skill → skillNotFound → `{success:false}` → `setActivities([])` → 空白且无报错。实例 B debug=false → 请求日志也被抑制，控制台无调用痕迹。

**修复**：
1. `SkillGateway.ts`：移除预创建的 `export const skillGateway = getDefaultGateway()`（第414行），改为注释说明"不要从本文件导入 skillGateway 实例"。`getDefaultGateway` 和 `resetDefaultGateway` 保留导出。
2. `skills/index.ts`：`new SkillGateway(...)` → `getDefaultGateway({ debug: process.env.NODE_ENV === 'development' })`，确保全局唯一单例。并增加 `import { getDefaultGateway }` 导入。
3. `useActivity.ts`：`import { skillGateway } from '../../skills/SkillGateway'` → `from '../../skills/index'`（正确的单例）。
4. `PublishedGameRuntime.ts`：`from '@/skills/SkillGateway'` → `from '@/skills/index'`（同上）。

**核心教训**：模块级 `export const` + barrel `new` 创建多个实例是隐蔽的 bug 源。**单例必须只在一处创建**（barrel 模块），其他文件通过 barrel 导出获取。**永远不要在类文件和 barrel 同时 export 同名实例**。

## 修复：道具不在游戏 props 栏显示（Effect Engine 方案变更）

**问题**：兑换码激活 invincible/super_mode/heal 后，游戏内 props（customPowerUps）不显示道具。平台 Effect Engine 自动执行效果（返回 true）→ 跳过 CustomEvent → 游戏的 `handleRedeemedItem()` 未触发 → customPowerUps 无新道具 → 玩家无视觉反馈。

**新方案（2026-07-23 实施）**：完全变更预设效果的处理策略：
- **invincible/super_mode/heal/restore_mp/give_weapon handler 全部返回 `false`**（不再自动执行，委托 CustomEvent + effectCode）
- **始终分发 CustomEvent**（不再按 `effectAppliedByPlatform` 条件跳过）
- **在 CustomEvent voucherData 中注入 `effectCode`**（本地玩家专属沙箱脚本）+ 修改 `effect` 名为 `_local_<effectType>`（避开游戏内置 forEach 全场误伤 handler）
- 游戏端 `handleRedeemedItem()` → 添加道具到 customPowerUps（props 栏可见）
- 玩家点击 → `useCustomPowerUp()` → `registerDynamicEffect()` → effectCode 执行 → 仅本地玩家生效

**effectCode 沙箱设计**：
- `findLocal` 内嵌函数：筛除 `controller.type==='AIcontroller'/'AIscript'` → 仅返回人类角色
- 通过 `game` 变量（sandbox 提供 = window.myGame）调用单角色 API（setInvincible/heal/restoreMp/giveWeapon）
- 躲避游戏方 forEach 遍历全场误伤，同时让道具在 props 栏正确显示

**同时修复**：
- `custom` handler 显式返回 `false`（不再返回 undefined 导致误判）
- `apply()` id-fallback：`effectType='custom'` 时用 `id` 字段查找已知 handler
- `effectKey` 查找同样增加 itemId 回退：`effectType='custom' + itemId='super_mode'` → 查找 `_LOCAL_PLAYER_EFFECT_CODES['super_mode']`
