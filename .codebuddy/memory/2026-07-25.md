## 修复：祖玛(zuma_effectcode.html) 道具在 PROPS 栏无法显示

**根因**：平台兑换道具后，SDK 在 iframe 内只通过 `allinone:item-redeemed` CustomEvent 派发道具（`GamePlay.tsx:324` 注释明确"不再单独发送 EXTENSION_VOUCHER"）。祖玛此前只监听 `EXTENSION_VOUCHER` postMessage 通道，漏掉 CustomEvent → 道具永远进不了 `customPowerUps` 背包 → PROPS 栏显示 "No items yet"。

**对照**：超级玛丽改造5.html 正常，因为它同时监听 `EXTENSION_VOUCHER`（postMessage）+ `allinone:item-redeemed`（CustomEvent），并在 `handleRedeemedItem` 中从 `detail.voucherData.effect` / `detail.itemId` 解析真实效果名。

**改动**：`AllinONE Online/zuma_effectcode.html` 新增 `handleRedeemedItem(detail)`，注册 `window.addEventListener('allinone:item-redeemed', ...)`。三优先级解析 effect：①voucherData.effect ②detail.itemId ③detail.effectType（都排除 'custom'）；含去重避免重复投送。SOP 的 7 个效果名与祖玛 EFFECT_HANDLERS 完全对应，道具可正常进背包并使用。

**可复用经验**：任何游戏接入平台 UGC 道具，必须监听 `allinone:item-redeemed` CustomEvent，不能只依赖旧的 EXTENSION_VOUCHER postMessage。

## 二次修复：祖玛兑换码道具"无内置效果"（effect=custom）

**现象**：兑换 `reverse_chain` 后控制台 `[Zuma] 解析道具: effect=custom`，点击 PROPS 栏报"未找到效果"，因为 `'custom'` 不匹配任何 EFFECT_HANDLERS。

**根因**：平台兑换码派发的 CustomEvent 中，`voucherData.effect` 与 `detail.effectType` 都是字面量占位 `'custom'`，**真实效果名在 `detail.itemId`**（如 `reverse_chain`）。首版修复的优先级 1 直接采用 `voucherData.effect`，未排除 `'custom'` → realEffect='custom' → 落到未知效果分支。

**改动**：`zuma_effectcode.html` 优先级 1 改为 `(voucherData.effect && voucherData.effect !== 'custom') ? voucherData.effect : null`，使其回落到优先级 2（`detail.itemId`）。修复后 reverse_chain 正确入背包且可点击执行。

**关键教训**：平台 redeem/统一下发路径下，`voucherData.effect` / `detail.effectType` 常为占位 `'custom'`，真实效果名优先看 `detail.itemId`。解析 effect 时务必排除字面量 `'custom'`。

## 文档更新：docs/allinone-publishing-guide.md

根据 Zuma 两次 bug（漏监听 CustomEvent + voucherData.effect='custom' 占位），更新发布指南，避免后来者/AI 复现：

1. §2.3 `handleRedeemedItem` 模板：优先级1 `voucherData.effect` 增加 `!== 'custom'` 排除，回落到 `detail.itemId`。
2. §2.4 警告框：补充 `voucherData.effect` 也可能是 'custom'；更正"voucherData 兑换路径可能不存在"为"通常存在（但 effect='custom'）"。
3. §7 检查清单：效果名排除 `'custom'` 占位。
4. §5 AI 提示词模板：必须监听 `allinone:item-redeemed` CustomEvent（原只写 EXTENSION_VOUCHER）；强调排除 `'custom'`。

**结论**：文档"双通道"框架正确，但模板代码/AI 提示词未正确排 'custom'、且 voucherData 存在性描述过时，现已对齐实测。

## 修复：新上传游戏线上「游戏文件不可用」(方案1+2)

**根因**（同前「游戏加载失败根因」记忆）：prod 前端在 CloudBase 静态托管域名，其所有 `/api/*` 请求被 `cloudbase.json` 的 hosting.rewrites(`**`→`/index.html`) 吞掉 → 后端不可达 → 模块化游戏强制 server 模式依赖的 SW 回退链（后端→Cache→IndexedDB）全断。

**方案1（后端可达，已实施）**：让 Service Worker 拦截**同域** `/api/*` 并代理到可运行时配置的后端基地址，而非逐个改绝对 URL（避免改 45 个文件、保留 SW 离线回退、协议通道跨域安全）。
- 新增 `public/config.js`：`window.__API_BASE_URL`（默认空，留空=同源相对路径；设值=后端 `/api` 基地址，例 CloudStudio `http://xxxx.codebuddy.cloudstudio.run:5000/api`）。
- `index.html`：在 module 前注入 `<script src="/config.js">`。
- `src/main.tsx`：新增 `syncApiConfigToSW()`，把 `window.__API_BASE_URL`(或 `VITE_API_BASE_URL`) 写入 Cache Storage `allinone-config/api-config`；SW 启动时 + 注册后各同步一次。
- `public/gameFileServiceWorker.js`：重写 `fetch` 监听——同源 `/api/` 全部 `event.respondWith(handleApiRequest)`；游戏文件 GET 走三级回退（①代理后端 ②Cache ③IndexedDB），其余 `/api` 直接代理后端，后端不可达返回 503 JSON。
- `server.js`：CORS `ALLOWED_ORIGINS` 增加 `https://allinonegaming-d4gmsmrzz573264f6.tcloudbaseapp.com`（前端静态域名，否则 SW 代理的跨域 fetch 被 CORS 拦）。

**方案2（SW 离线兜底对小游戏生效，已实施）**：`publishedGameService.ts` 的 `saveGameFiles` 原逻辑：小游戏(<4.5MB)写 localStorage 后 `deleteFromDB` → SW（只读 IndexedDB）无法离线回放。改为**始终写 IndexedDB**（localStorage 仅作页面同步读取加速层）。SW 另在后端成功时 `persistToIDB` 把每个游戏文件（文本直存、二进制转 `__BINARY_BASE64__`）写回 IndexedDB，玩家首次在线加载后即获耐久离线兜底。

**部署要点**：
- CloudStudio 后端：`USE_MEMORY_DB=true PORT=5000 node server.js`（或 PORT=3000）。
- **必须**把 `public/config.js` 的 `window.__API_BASE_URL` 设为后端 `/api` 基地址（CloudStudio 预览 URL 每次重部署会变，需同步改 config.js 并重新部署前端）。若直接通过后端预览 URL 访问应用（server.js 同源托管前端+后端），config.js 留空即可。
- 前端 `pnpm run build:client` → 部署 dist/static 到 CloudBase 静态托管；旧 SW 缓存需在浏览器清一次（或等 skipWaiting/clients.claim 生效）。

**验证**：`node --check` 通过；`build:client` 用 vite/esbuild 不做类型检查，既有 publishedGameService.ts:646-647 等预存类型错误不阻断本次打包。

## 自查 bug：方案1+2 引入的回归（已修复）

**Bug（严重，回归）**：SW 原拦截**所有**同源 `/api/`，且 `config.js` 留空（dev 与同域 server.js 部署的默认）时 `proxyToBackend` 返回 null → `handleApiRequest` 直接 503。后果：dev 模式（vite `/api`→:3000 代理）与同域生产部署下，整个应用所有 `/api` 调用全 503 崩掉。
**修复**（`public/gameFileServiceWorker.js`）：新增 `handleRequest`，`getApiBaseUrl()` 为空时**放行走默认网络** `fetch(req)`（恢复 dev/同域行为），仅在配置了后端基地址时才代理到后端。SW 自身 `fetch(req)` 不会触发自身 fetch 监听，无死循环。
**附带优化**（`src/main.tsx`）：SW 注册从 `window load` 提前到模块加载即执行，配合 `skipWaiting`+`clients.claim` 缩小首屏 `/api` 命中 CloudBase rewrite 的竞态窗口。

**已确认无误项**：存储 `path`=相对路径，SW `parsed.filePath`=相对路径，精确匹配；`vite-env.d.ts` 已声明 `VITE_API_BASE_URL`（无类型错误）；后端 `GET /:gameId/files/*` 正确解码 `__BINARY_BASE64__`；CORS 放行静态托管域名。
