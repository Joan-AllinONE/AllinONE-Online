### 改动清单
- **后端** `cloudfunctions/gamesApi/index.js`：
  - `GAME_SVC_COLLECTIONS` 增加 `quests` / `quest_claims` / `quest_submissions` 3 个集合

## Bug 自查修复（同日）

1. **[严重] questService 读方法 isApiAvailable 守卫错误**：`isApiAvailable()` 用 `getCachedToken() !== null` 同步缓存检查，首次访问 token 未缓存时 listQuests/getQuest/listSubmissions/listMods 恒返回空；而 apiFetch 内部本用 `await getToken()` 异步获取。已删除 isApiAvailable 函数 + getCachedToken import + 4 处守卫，统一由 apiFetch 的 getToken 处理。
2. **[健壮性] merge 缺 quest.status 校验**：已加 `if (quest.status === 'merged' || 'closed') return 400`，防止重复合并/重复发报酬。
3. **[健壮性] vote 缺 submission.status 校验**：已加 `if (doc.status !== 'reviewing') return 400`，防止已合并/已通过提交被投票降级回 approved。
4. **[UI 状态] 关闭/合并后弹窗状态不同步**：QuestPlaza 新增 `handleChanged`，onChanged 时除 load 外还 `getQuest(selected.id)` 刷新 selected，弹窗内按钮/状态即时更新。
5. **[UI 筛选] STATUS_TABS 去掉 'review'**：后端从不产生 review 状态的 quest（quest 只有 open/merged/closed），改为加 'closed' 筛选。

### 经验教训（长期）
- 读 API 服务不要用「同步 token 缓存检查」做守卫——会用 `getCachedToken() !== null` 误伤首次访问；统一用异步 `getToken()`。
- 所有写路由（merge/vote/review/claim）都应校验目标实体当前状态，防止重复操作/状态降级。

## 修复：社区广场白屏（isApiAvailable 残留 + list 返回 null）

- 现象 1：`questService.ts:30 Uncaught ReferenceError: isApiAvailable is not defined`。
  根因：上一轮删除 isApiAvailable 函数定义时，`listQuests`/`listSubmissions` 的 `if (!isApiAvailable()) return []` 调用**未删净**（并行 replace 快照冲突，只删掉了 getQuest/listMods 两处）。已用 `replace_all` 彻底清除，`search_content` 确认 0 残留。
- 现象 2：`QuestPlaza.tsx:244 TypeError: Cannot read properties of null (reading 'length')`。
  根因：`apiFetch` 返回 `json.data`，dev 模式下后端（SW 对非游戏 API 返回 `{success:true,data:null}`）返回 `data:null`，`listMods` 把 null 塞进 `mods` state → `mods.length` 崩溃。
  修复：`listQuests`/`listSubmissions`/`listMods` 三个 list 方法返回值统一加 `|| []` 兜底，绝不返回 null。

### 经验教训（长期，重要）
- 并行对同一文件做多个 `replace_in_file` 时，若 old_str 相互接近/依赖，可能因快照冲突导致**部分替换静默未生效**（返回成功但实际没改，或反之）。改完必须 `search_content` 验证残留，不能只信 replace 的返回。
- 所有「列表类」API 服务方法的返回值必须 `|| []` 兜底，防止后端 `data:null` 导致 `arr.length`/`arr.filter` 崩溃白屏。单对象类（getQuest）保持 null 语义（表示未找到）。

### 现象
发布任务报「发布失败，请检查是否已登录」，但实际已登录。

1. **直接根因（环境）**：CloudBase 云函数返回 `FUNCTIONS_INVOCATION_FAILED` + `AvailableStatus = InsufficientBalance`（**余额不足，云函数整体不可用**）。所有云函数请求（dev-token、各集合、任务发布）都 400。这也解释了 dev 日志里大片 `dev-token 400`/`users 400`/`vouchers 400`。

### 已做修复
- `questService.ts` + `QuestAPI.ts`：`API_BASE = getFeatureApiBase('quests')` → `API_BASE = \`${getApiBase()}/__quests\``，dev/prod 统一走云函数 `__quests` 隧道。

### 待办（需用户）
- **充值 CloudBase** 恢复云函数（余额不足是当前阻塞主因）。
- 充值后**部署云函数** `gamesApi`（本地 `cloudfunctions/gamesApi/index.js` 已加 `__quests` 隧道，但未部署）。

## 修复：dev 下游戏加载 "File not found"（server.js 缺 __files 端点）

### 现象
dev 发布/打开游戏报 `{"success":false,"error":"File not found: 超级玛丽改造5.html"}`。

### 根因
`publishedGameService.saveGameFiles` 第③步调用 `POST ${GAMES_API_BASE}/__files` 把游戏文件批量写入后端 `game_files`。但 **server.js（本地后端）没有 `POST /__files` 端点**（只在云函数 gamesApi 有），dev 下该请求失败 → 文件只存浏览器本地（IndexedDB/localStorage），本地后端无文件 → 加载 `GET /:gameId/files/*` 报 "File not found"。

### 修复
`src/server/routes/games.ts` 的 `createGamesPublicRouter`（公开、authMiddleware 之前、无 JWT，与前端调用一致）新增 `POST /__files`：
- body `{ gameId, files: [{ path|name, content, size? }] }`，限制单文件 10MB / 总量 100MB
- 内存库走 `memoryDB.saveGameFiles`；PostgreSQL 走 `INSERT ... ON CONFLICT (game_id, file_path) DO UPDATE`
- 复用 `getMimeType`、`express.json({ limit: '150mb' })`（与 upload 端点一致）

### 验证（已通过）
- `tsc -p tsconfig.server.json` EXIT=0，lint 0
- 重启 server.js 后：`POST /api/v1/games/__files` → 200 `{saved:1}`；`GET /api/v1/games/test-game/files/hello.html` → 200 返回文件内容

### 注意
- 历史游戏（文件在云函数/未重新发布）在 dev 下本地后端无文件，需**重新发布**一次让文件写入本地 server.js；SW 有 IndexedDB 兜底（但小游戏写 localStorage，SW 不读，兜底失效——既有问题）。
- server.js 启动较慢（约 8 秒），kill 后重启要等监听。
