# 2026-09-08 工作日志

## 修复发布失败「logger.warn is not a function」

- 根因：审核机制在 `PublishingPipeline.stepPublish` 新增的提交审核块里用了 `logger.warn(...)`，但管线自定义 `Logger` 类只有 `info/success/error/warning`（没有 warn）。
- 连锁失败链：submit 成功但 autoChecks 有 fail 项（本地常态）→ 第 1 处 logger.warn 抛 TypeError → 被我的 try/catch 捕获 → catch 里又调 logger.warn → 再抛且无人捕获 → stepPublish 整体失败 → 用户看到「发布失败 logger.warn is not a function」。
- 修复：3 处 `logger.warn` → `logger.warning`（PublishingPipeline.ts ~818/822/825 行）。
- 教训（通用）：**publishing-center 的 PipelineLogger API 是 `warning` 不是 `warn`**；在管线步骤里新增的副作用块必须保证任何内部错误都不会让发布流程失败。
- 另：PlatformAdmin 顶部导航已加「游戏审核」入口按钮（09-06 追加，ShieldCheck 绿色图标 → navigate('/game-review')）。

## 修复 Match3 道具永不掉落（isPlatformMode 恒 false）

- 根因：发布管线 Mode A（`PublishingPipeline.injectProtocolIntoFiles`）只注入 `<head>` 协议层 + `</body>` 前兑换条 SDK，两者只设置 `window.AllinONE`（`__GAME_ID__`/`GAME_ID`），从不注入 `window.__ALLINONE_CONFIG__`；`SkillInitializer.injectConfigToGamePackage` 全流程无人调用（死代码）→ 游戏 `init()` 判定 `isPlatformMode=false` → `dropHarvestItem()` 第一行静默 return。道具永不掉落、P1 面板恒空、零报错。
- 修复（双保险，已实施 + vite build 通过 39.09s）：
  - 方案 A（游戏侧）：`Match3Game_effectcode.html` 新增 `ensurePlatformMode()` 懒检测（`__ALLINONE_CONFIG__` 或 `AllinONE.__GAME_ID__`/`GAME_ID` 任一存在 → isPlatformMode=true，并剔除无 origin 的 demo 示例道具；UGC 兑换道具本就无 origin 不受影响），`dropHarvestItem` 首行改 `if (!ensurePlatformMode()) return;`
  - 方案 B（管线侧根治）：`PublishingPipeline.ts` Mode A 新增 `generateConfigScript(gameId)`，注入 `<script>window.__ALLINONE_CONFIG__={gameId,platform:'allinone',sdkVersion:'1.0.0',injectedAt}</script>` 到 `<head>`（三个无 head 变体分支均覆盖；内容已含 `__ALLINONE_CONFIG__` 时跳过防覆盖）
- 生效条件：方案 A 需**重新发布 Match3 游戏**；方案 B 只帮到未来发布。
- 编辑纪律再验证：同一文件两处编辑分两批串行执行（跨文件并行），事后 grep 四处修改点全部落盘确认。

## 修复「购买道具后不可用」+「跨游戏适配无效果」（ProtocolEngine 双实例）

- 现象：道具凭证提取/上架/购买都成功，但购买后道具无法进游戏；GameStore「来自其他游戏的道具→适配到本游戏」也无效果。控制台矛盾日志：GamePlay「协议通道已建立」后 voucherItemService 下发报「游戏通道不存在」。
- 根因：**双 ProtocolEngine 实例**。GamePlay.tsx 曾 `new ProtocolEngine({...})`（own channels + onRedeem 回调）；而 `ProtocolEngine.ts` 模块级 `export const protocolEngine = getDefaultEngine()` 在 import 时已创建无配置单例，voucherItemService.redeemItemVoucherBySchema 走 `getDefaultEngine().sendToGame` → 单例 channels 空 → sendToGame false →「游戏通道不可用」。凭证因 dispatched 检查（936-938 提前 return）未被误标记已使用，资产无损。
- 修复（9 处，build 通过）：
  - ProtocolEngine.ts：新增 `ensureConfig(config)`（merge 补挂回调）+ `releaseChannel(gameId)`（delete 单通道）
  - GamePlay.tsx：`new ProtocolEngine` → `getDefaultEngine()+ensureConfig`；cleanup `destroy()` → `off('game:event', gameEventHandler)+releaseChannel(gameId)`；game:event 内联回调提取为具名 `gameEventHandler`（防单例 listeners 累积重复处理）
  - backendSync.ts：dev-token body `JSON.stringify({})` → `{userId: getCurrentUserId()}`（修本地 400 Missing userId + 连锁 extension_vouchers 401；云函数匿名串号隐患一并修）
- 道具兑换两条既有路径（用户须知）：①兑换码：GameStore 购买后复制 redeemCode → 游戏内兑换条输码 → REDEEM → GamePlay onRedeem（挂单例 config）→ verifyCode/useCode → REDEEM_RESULT；②自动下发：GameStore「兑换到游戏」失败时提示跳转 `/game/:id?itemVoucher=voucherId` → GamePlay 轮询通道就绪后 redeemItemVoucher 下发。双实例 bug 修复后两条均通。
- 跨游戏适配原理（P2b）：`redeemItemVoucherBySchema` 检测 customData.gameId !== request.gameId → 源凭证留痕 + ExtensionVoucherService.adaptForGame 生成适配凭证（effect 通用字段保留，schemaName 按目标声明映射）→ sendToGame 下发 payload 带 adapted:true/sourceGameId。此前失败即双实例根因。
