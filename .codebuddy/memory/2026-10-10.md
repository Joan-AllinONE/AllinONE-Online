## GSO 三问题（用户实测）：发起权限 / 认购托管 / 期限结算
- **问题1（无份额账户可发 GSO）**：deploy 原只校验「issuerId=登录身份」，未校验游戏份额归属。修复（contractTunnel.ts + 云函数 index.js:3964 双实现）：gso deploy 时查 published_games，`game.publisherId !== userId` → 403「只有游戏发布者（份额持有者）可发行」；游戏档案缺失 → 404。云函数 doc().get() 形状兼容 `(data[0]||data).publisherId`。
- **问题2（认购后托管金额没扣）**：执行层 escrowLock 本身正确（walletTransfer fromUserId≠'escrow' → escrowLock 扣款进托管）。**根因=影子模式**：CONTRACT_AUTO_EXECUTE 只从 env 读，用户启动 server.js 没带 env → gso/全档 autoExecute=false → 认购只入 plan 不动钱。修复（config.ts）：`USE_MEMORY_DB=true` 时 dev 缺省 `group-buy,team-quest,gso` 全开；生产（无 USE_MEMORY_DB）仍必须显式设 env，灰度顺序不变。
- **问题3（0.1h 期限不结算）**：`POST /__contract/tick` 端点存在但**本地无任何定时器调用**（云函数有 timer trigger）。修复（server.js）：`USE_MEMORY_DB` 时 setInterval 60s fetch 自身 tick（.unref()）；幂等安全=确定性 triggerId 时间桶+saga txId。tickBucket：deadline-check=1h 桶，closeAt 过后首 tick 即结算。
- **超额认购规则**（用户问）：hardCap/perUserCap 先到先得；未设 hardCap 可超额，交割时全额给发行方、RSV 按认购金额占比分配（不退回不缩减）——逻辑本已如此，gso.ts description 补充规则说明。
- 验证：云函数 node --check OK；tsc server 0 错误；lint 0。**全部生效需重启 server.js**（config/tick/影子默认均为启动时求值）。
- 教训：本地 dev 与云函数的执行环境差异（timer trigger 有无、env 缺省值）会造成「线上正常本地坏」的错觉类 bug。

## 拼团/组团合约资金审查（用户要求：另两模板是否有相同问题）
- **安全项（已有保障）**：escrowLock/escrowForfeit 均有余额守卫；refundAll 按台账逐条原路退（天然不超发）；三模板全部 cron 条款 then 含 setState → 状态离开 enabledStates 自然幂等；两模板 cron enabledStates ⊆ tick targets ✓ 60s tick 全覆盖。
- **修复合集**：
  1. **escrowRelease 调序**（contractTunnel.ts + 云函数 index.js:3785 双实现）：原「先给收款人入账后验台账」→ 余额不足时收款人已拿钱、台账未扣，实例回滚后台账与实际资金不一致。改为先扣台账（验证充足）后入账。
  2. **TeamQuest P-F（团长不注资奖池）**：tq-settle/tq-settle-empty 从空托管转出 → throw 死信 → 保证金也卡死。修：两条款 when 加注资守卫 `(params.rewardPool.amount == 0 || state.poolFunded == 1)`。
  3. **TeamQuest P-H（active 中途退出致人数<min 过截止）**：tq-settle 要求≥min、tq-refund 仅 signing → 资金永久卡死。修：新增兜底条款 `tq-settle-unfunded`（人数足+未注资 → refundAll(bond)+settling）与 `tq-settle-understaffed`（人数不足 → refundAll(pool) 原路退发起人 + refundAll(bond) + settling）。三态完备。
  4. **P-G（重复 leave 重复领保证金）**：靠 escrowRelease 守卫天然拒绝（第二次退出因托管余额不足 throw、saga 整体回滚）——资金安全，体验为报错，可接受。
- **未修（语义偏差，非资金安全）**：groupBuy 满员交割（gb-reach-max 可能远早于 closeAt）后卡在 settling 至 closeAt+disputeWindow——挑战窗口被拉长，可 dispute 设计如此。
