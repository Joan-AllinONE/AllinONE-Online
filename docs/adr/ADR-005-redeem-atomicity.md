# ADR-005: 兑换码原子化方案

**状态**: 已接受  
**日期**: 2025-06-07

## 上下文

兑换码核销存在经典竞态条件：`verifyCode` 和 `useCode` 之间无原子性保证，可导致双花（同一兑换码被多次使用）。

## 决策

采用 **代码级互斥锁 + PostgreSQL 行锁** 双层保障：

### 内存模式（开发环境）
```
redeemLocks: Map<code, Promise> → 串行化同码操作
useCode() → 锁内 check-and-use → 仅第一个请求成功
```

### PostgreSQL 模式（生产环境）
```sql
SELECT * FROM redeem_codes WHERE code = $1 FOR UPDATE;
-- 行锁阻塞并发请求
UPDATE ... WHERE status = 'active';
-- 仅 active 状态可更新
```

## 替代方案

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 乐观锁（版本号） | 无锁等待 | 需重试机制 | ❌ |
| Redis 分布式锁 | 高性能 | 需额外基础设施 | ❌ |
| 代码级互斥 + PG 行锁 | 无需额外依赖、双重保障 | 代码互斥为进程内 | ✅ |

## 影响

- 内存模式的互斥锁仅在单进程内有效（生产环境需 PG 行锁）
- 兑换码端点已配置严格速率限制（10req/min）作为额外防护
- 未来可引入 Redis 分布式锁实现多进程互斥
